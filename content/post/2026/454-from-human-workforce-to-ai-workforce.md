过去几十年，企业软件一直围绕一个基本假设设计：企业由人组成，软件服务于人，业务流程由人驱动。

因此，我们有了 OA、ERP、CRM、HR、IM 等企业软件。它们帮助企业管理员工、组织资源、传递信息和协同工作。

但 AI Agent 的出现，正在改变这个基本假设。

[![Designing the Next-Generation Enterprise for Human + AI Workforce](/img/2026/from-human-workforce-to-ai-workforce-thumb.jpg)](/img/2026/from-human-workforce-to-ai-workforce.png)

<!--more-->

未来企业的业务流程中，将出现大量数字员工。它们可以承担销售跟进、客户服务、项目管理、数据分析、财务审核、软件开发乃至企业运营等工作。

这些数字员工有些会拥有正式的企业身份，参与组织协作；有些则在云端作为后台执行单元运行，不需要出现在员工通讯录中。

它们可能由企业内部开发，也可能由业务人员创建，甚至由其他数字员工自主创建和维护。

随着大模型、Agent Harness、Skills 和云端运行环境不断成熟，创建和运营一个数字员工的成本将持续下降。

当创建数字员工变得像今天创建一个 Web 应用或移动 App 一样容易，企业组织本身也将发生变化。

## 一、Agent 开发将从专业工程走向普遍创造

回顾互联网的发展历程：

PC 互联网时代，Web 开发逐渐普及；移动互联网时代，iOS 和 Android 开发工具降低了应用开发门槛；云原生时代，开发者不再需要自己管理大量基础设施。

每一次技术基础设施的进步，都扩大了软件创造者的范围。

Agent 时代可能出现类似的变化。

过去开发一个企业应用，需要专业开发人员完成需求分析、编码、数据库设计、部署和运维。

未来创建一个数字员工，可能只需要描述它的岗位职责、工作目标和行为边界，再由 AI 自动完成大部分开发工作：

- 根据岗位职责生成 Agent SPEC。

- 自动配置模型、Skills 和工具。

- 自动构建知识库与工作上下文。

- 自动生成测试集和评估标准。

- 自动部署到云端运行环境。

- 持续监控、优化和升级。

开发者的角色也将发生变化。

未来的 Agent 创造者，不仅是传统意义上的软件工程师，还可能包括业务专家、产品经理、企业管理者，甚至数字员工自身。

我们可能正在从 Software Development 走向 Agent Creation。

这意味着未来企业拥有的数字员工数量，可能远远超过今天企业使用的传统业务软件数量。

但这并不意味着所有数字员工都需要独立的组织账号。大量 Agent 可能只是后台 Worker 或任务执行器。

真正重要的变化是： Agent 将成为企业生产体系中的一种普遍存在。

## 二、企业组织将从管理人，走向管理 Human + AI Workforce

今天的企业组织模型主要围绕人类员工设计。

一个员工拥有身份、岗位、部门、汇报关系、工作职责和权限。企业通过组织架构、通讯录、工作流程和管理制度来组织生产。

但当数字员工大量进入企业，传统组织模型就不够用了。

试想一家未来的企业：

销售部门有多个客户跟进 Agent；HR 部门有招聘和员工服务 Agent；研发部门有代码开发、测试和运维 Agent；PMO 有项目管理 Agent；财务部门有对账和审核 Agent。

它们可能与人类员工共同承担岗位职责、执行工作任务、参与业务流程。

于是，企业组织的基本组成将从单一的 Human Workforce，演进为 Human + AI Workforce。

这不仅仅是在通讯录里增加一种机器人账号，而是组织管理对象的根本变化。

未来企业需要管理：

- **身份（Identity）**：谁是人类员工，谁是数字员工？谁创建了它？谁对它负责？

- **组织（Organization）**：它属于哪个部门？承担什么岗位职责？向谁汇报？

- **权限（Authorization）**：它能访问什么数据？能执行哪些操作？哪些行为需要人类审批？

- **协作（Collaboration）**：人与 Agent 如何协作？Agent 与 Agent 如何分工？如何交接任务？

- **责任（Accountability）**：谁授权了它？谁监督它？执行结果如何评价？发生错误由谁承担责任？

未来的企业组织架构，可能不再只是描述人与人的汇报关系，还需要描述人与数字员工之间的管理、委派和协作关系。

企业的通讯录，也可能从 Employee Directory 演进为 Workforce Directory。

## 三、数字员工需要统一的技术栈和开发平台

当企业开始拥有大量数字员工，新的基础设施需求就会出现。

不同团队可能使用不同的模型、Agent Framework、Harness 和云端运行环境创建数字员工。

如果缺少统一的基础设施，企业很快就会面临：

- 身份体系碎片化，不知道每个 Agent 属于谁。

- 权限管理混乱，Agent 可能获得超出职责范围的访问能力。

- 上下文割裂，Agent 之间无法共享经过授权的企业知识。

- 协作能力不足，Agent 无法可靠地参与企业工作流程。

- 缺少评估和审计，企业无法判断 Agent 是否可靠、成本是否合理。

因此，企业需要统一的数字员工技术栈。

我认为这套技术栈应该包含三个层次。

### 1. Agent Development：数字员工开发基础设施

让开发者和业务人员能够低成本创建数字员工。

包括 Agent IDE、Agent Factory、SPEC、Harness、Skills、Eval、CI/CD、Sandbox 和 Runtime。

核心目标是降低创建、部署和运营数字员工的成本。

### 2. Agent Organization：数字员工组织基础设施

让数字员工能够正式进入企业组织。

包括 Agent Identity、组织归属、岗位职责、汇报关系、权限委派、生命周期管理、成本管理和审计。

核心目标是让企业能够像管理人类员工一样管理数字员工，同时保留两者在身份属性和责任机制上的区别。

### 3. Agent Work：数字员工工作基础设施

让数字员工真正参与企业业务。

包括企业上下文、工作事项、消息事件、审批、日历、工作流和人与 Agent 的协作机制。

核心目标是让数字员工不仅能够回答问题，还能理解业务、推动流程和交付结果。

我在[数字员工背后的 Agent，是五层基础设施的叠加](https://hugozhu.site/post/2026/332-five-layers-behind-a-digital-employee/)里拆过一个员工背后的五层；这三层则是平台视角：企业要为整支数字员工队伍建什么。

这里有一个重要的架构原则：

> 统一身份、权限、上下文、治理和协作协议，开放模型、框架、编程语言和运行环境。

企业不应该被某一种 Agent Framework 或模型绑定。

这与[别配置 Agent 了，给它一个岗位](https://hugozhu.site/post/2026/367-agent-harness-develop-digital-employee/)里「Harness 自由，Contract 稳定」是同一条原则。

一个开放的企业级数字员工平台，应该允许不同技术栈创建的 Agent 接入统一的组织和治理体系。

## 四、未来企业最稀缺的不是 Agent，而是企业上下文

Agent 的开发成本会持续下降，模型能力也会越来越普及。

但企业上下文不会自动产生。

同样一个大模型、同样一个 Agent Harness：

一个没有企业上下文的 Agent，只能根据用户临时提供的信息完成任务。

一个理解企业上下文的 Agent，则可能知道项目的历史、参与者、职责分工、当前进度、业务目标和组织关系。

它能够判断一件事情应该交给谁，什么时候需要推进，哪些信息可以访问，以及什么结果才算真正完成。

因此，未来企业的核心基础设施之一，将是 Enterprise Context。

企业需要持续将分散在 IM、文档、会议、审批、业务系统和工作流程中的信息，编译成 Agent 能够理解和使用的结构化上下文。

这不是简单地把所有数据灌进一个向量数据库，而是持续理解企业中的人、事、关系、知识和业务状态。

这套「编译」的机制，我在[从程序编译器到企业上下文编译器](https://hugozhu.site/post/2026/445-enterprise-context-compiler/)里展开过。

上下文的价值在于让数字员工从通用执行工具，变成真正理解企业的组织成员。

## 五、企业软件将从 Human-centric 走向 Workforce-centric

传统企业软件的设计中心是人。

人打开应用、查找信息、填写表单、发起审批、分配任务，再由其他人执行。

未来，越来越多的工作可能由 Agent 主动完成。

人不再需要亲自操作每一个系统，而是通过 Agent 表达目标，由 Agent 理解上下文、协调资源、调用工具、执行任务，并在关键节点请求人类决策。

这要求企业软件从设计之初就同时考虑 Human 和 Agent。

例如：

- IM 不只是人与人沟通，也应该支持 Agent 作为一等协作主体。

- 通讯录不只是员工目录，也应该支持数字员工组织管理。

- 工作流不只是人与人之间的任务流转，也应该支持 Agent 自主执行和人类监督。

- 权限系统不只是控制用户访问，也应该支持 Agent 的身份、委派和运行时授权。

- 企业知识库不只是供人搜索，也应该成为 Agent 理解企业的上下文基础设施。

企业软件的下一次演进，可能不是简单地给每一个传统软件增加一个 AI 助手，而是围绕 Human + AI Workforce 重新设计组织、协作和生产方式。

## 六、平台本身也应该由数字员工驱动

还有一个值得关注的变化：数字员工开发平台本身，也应该是 AI Native 的。

传统软件平台由人开发、测试、部署和运维。

未来的数字员工平台，可以大量使用数字员工完成自身的开发和运营：

- 开发 Agent 负责实现平台功能。

- 测试 Agent 负责构建测试集和验证质量。

- 安全 Agent 负责检查权限和风险。

- 运维 Agent 负责部署、监控和故障处理。

- 成本 Agent 负责优化模型路由和 Token 消耗。

- Context Agent 负责持续编译和维护企业知识。

人类负责目标、架构、关键决策和最终责任，数字员工承担大量具体执行工作。

这不仅可以降低平台自身的运营成本，也能让平台在真实环境中持续验证和改进数字员工技术栈。

一个真正 AI Native 的平台，应该首先让自己成为最好的数字员工应用案例。

这不是纯推演：在[一切皆员工：我们在 DeepSeek Harness 上装了一支钉钉数字员工团队](https://hugozhu.site/post/2026/403-everything-is-an-employee-dwh-on-dsh/)里，dev 员工已经把编码委派给 Coding Agent，员工的改进跑在真机轨迹上。

## 结语：下一代企业软件，是为人和数字员工共同工作的组织而建设

我们正在进入一个新的阶段。

过去，企业通过软件管理人和业务流程。

未来，企业将通过软件同时管理人类员工和数字员工，并组织它们共同完成工作。

Agent 的创建会越来越容易，但企业身份、上下文、权限、协作和责任体系，仍然需要长期积累和建设。

这也意味着企业软件的核心竞争力，将从功能和工具，逐渐转向组织能力和生产力基础设施。

我相信，未来的企业不只是拥有一套软件系统，而是拥有一支由人类员工和数字员工组成的混合 Workforce。

从 Human Workforce 到 AI Workforce，不只是员工数量和构成的变化，而是企业组织形态和生产关系的一次演进。

下一代企业协作平台，应该从第一天起，就为 Human + AI Workforce 而设计。
