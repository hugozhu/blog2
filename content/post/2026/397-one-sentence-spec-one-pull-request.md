那天我想找自己四年前写的一篇 Tailscale 笔记，按了 ⌘K，然后盯着一个白色的框看了几秒。

不是几百毫秒的那种「几秒」，是你会忍不住去点一下别的地方、怀疑自己是不是没点中的那种几秒。这个博客到今天有 388 篇文章，搜索是我自己用得最多的功能——而它是我自己的网站上，唯一一个让我等的地方。

底下那套东西我大概记得：一个叫 Pizza 的 WASM 全文检索组件，两年前接的，作者早就不更新了。每次有人打开搜索框，浏览器要先把整站的 `/index.json` 拉下来——4.6 MB 原文，gzip 后 1.7 MB——再在 WASM 里从头建一遍索引。文章越写越多，这个「从头建一遍」就越来越贵。

这件事我拖了半年没动。这次我没自己动手，我把它交出去了。

## 一、我提的需求，只有一句话

协作方是 Grok Bot。我给它注册了一个 GitHub 账号，把仓库地址甩过去——这是个 public repo，内容、模板、构建脚本、CI 配置全在里面。

然后我说了一句话：

> 我 Blog 上的搜索基于一个几乎没人维护的组件，内容越来越多之后变慢了，给我一个更优的方案。

没有技术选型，没有约束条件，没有「不许引入 Node 依赖」这类护栏，也没有告诉它 Pizza 是什么、`index.json` 从哪来。我甚至没说清「慢」是慢在哪一步——这一点后面会回来找我。

三个多小时后（09:17 UTC 提交），一个 PR 出现在仓库里：**15 个文件，+676 / −26**。

## 二、它交回来的不是代码，是一次架构选择

打开 PR 描述，第一段就把问题重新定义了一遍：

> Without a backend, search feels slow mainly because the browser re-ingests a full-text `index.json` on every visit.

它没有去优化 WASM，也没有去换一个更快的检索库。它换掉的是 **索引在什么时候建**：

```text
旧路径：  访问 → fetch /index.json (4.6MB) → WASM 里现场建索引 → 查询
                 └────────── 每次访问都重来一遍 ──────────┘

新路径：  CI 构建 → 倒排 postings + 精简 docs meta → 静态文件
          访问 → fetch segment.json → 存进 IndexedDB → Worker 里查
                                      └─ 第二次访问零网络 ─┘
# generated by hugo AI
```

具体交付物：

- `scripts/build-search-index.mjs`（225 行），构建期把文章切成 Latin 词 + 中文 uni/bi-gram，产出倒排表 `postings` 和只含 title / url / tags / summary 的 `docs`——**正文不进首屏 payload**；
- 产物按 buildId 哈希命名，配一个 `latest.json` 做指针，避免旧的 build-meta 指向已经不存在的段；
- 运行时挂进原有的 `#docsearch` 容器，查询扔进 Web Worker，不占主线程；下载完的段按 buildId 存 IndexedDB；
- 改了 `.github/workflows/hugo.yaml`，在 Hugo 之后加一步，从 `public/index.json` 重建索引——这样 Permalink 用的是 Hugo 真正生成的那个；
- 删掉了旧的 WASM 包（919 KB 的 `.wasm` 加一个 JS bundle），但保留了 DocSearch 兼容的 CSS，导航栏那颗按钮长得一模一样；
- 顺手写了一份 `SEARCH.md`：架构、构建命令、新旧对比表、五条测试清单。

最终索引里有 160,170 个 term、388 篇文档。

我想强调的不是「它会写代码」——这个 2024 年就不新鲜了。我想强调的是三件更靠上的事：**它自己定义了问题**（慢的根因是运行时建索引，不是查询算法）、**它自己改了流水线**（知道产物得在 CI 里重建才有正确的 Permalink）、**它自己给下一个人留了文档**（SEARCH.md 就是我一直在说的那种 [把「为什么」写进版本库](https://hugozhu.site/post/2026/388-runbook-write-why-into-repo/)）。

这三件事，在传统分工里叫「技术方案」「发布流程」「交接文档」，通常需要三次会议。

## 三、我做的第一件事：merge

12:43 UTC，我点了 Merge。

从提交到合并，中间隔了三个多小时，但那三个小时里我在开会。真正花在这个 PR 上的时间：拉下来跑一遍 `hugo server -D`，按 ⌘K，搜「树莓派」，出结果，关掉。**不到二十分钟。**

然后 GitHub Actions 自己跑起来：Hugo 构建 → 重建索引 → 推到 Pages 仓库 → 钉钉群里弹一条部署通知。我什么都没做。

这条链路值得单独说一句：**它之所以能一路自动跑到线上，是因为 CI 本来就是这个仓库的一部分。** Bot 能改 `hugo.yaml`，是因为 `hugo.yaml` 在它能看到的地方；改完能立刻验证，是因为 merge 到 main 就等于上线。如果我的部署流程是「找运维在跳板机上执行一个脚本」，这个 PR 到我这儿就断了——它交付的东西再完整，也只能停在我的硬盘上。

## 四、我做的第二件事：线上验收，然后发现它没错，但也没对

晚上我在手机上打开自己的博客，连的是家里那条不太行的 Wi-Fi。

按 ⌘K——**白屏**。等了几秒才出结果。跟改之前的手感几乎一样。

去看 Network，数字很清楚：

| | 旧：Pizza WASM | 新：静态索引 |
| --- | --- | --- |
| 首屏传输量（gzip） | 1.7 MB | **2.3 MB** |
| 下载完之后 | 现场建索引 | 直接可查 |
| 查询耗时 | 几十到几百 ms | 几 ms |
| 第二次访问 | 全部重来 | IndexedDB 命中，零网络 |

看到没有——**首屏 payload 反而变大了。**

这不是 bug，是这个架构的必然代价：倒排表本来就比原文冗余。它换来的是「下载完之后什么都不用干」和「第二次访问不用下载」。从总账上算，这笔交易是划算的，而且划算得多。

但我按下 ⌘K 那一刻感受到的「慢」，一点都没变。

更糟的是我接着试出来的两件事：

1. **索引没加载完的时候输入的查询，被直接丢掉了。** 你打完字，回车，什么也不发生，得再敲一次。
2. **如果 `segment.json` 请求失败**（我把网断了试的），页面上什么反馈都没有——错误只往 console 里扔了一行，用户看到的是一个永远空着的搜索框。

再往代码里翻，还有两个作用域 bug：`ui.renderPhase` 压根没暴露出来，Worker 的 ready 回调里 `lastQuery` 引用是坏的。这两个 bug 的共同点是——**它们只在索引还没加载完的那段时间里才有机会执行。** 在开发机上，那段时间是 0.2 秒；在我家的 Wi-Fi 上，那段时间是 8 秒。

于是我补了一个 commit（+98 / −7）：流式读取 response body 报下载进度（百分比 + MiB）、把加载期间输入的查询记下来等索引就绪后重放、加一个显式的「搜索索引加载失败」错误态、修掉那两个作用域 bug。

现在按 ⌘K，你会看到「正在加载搜索索引… 43% (1.0/2.3 MiB)」。**加载时间一秒没减少，但那几秒不再是白屏了。**

## 五、AI 优化的是你说的那个词

复盘一下这次协作里唯一真正出问题的地方。

我说的是「**搜索变慢了**」。

Bot 听到的是 query latency——它在 PR 的测试清单里写得明明白白：`hits should return in a few ms (footer shows worker timing)`。它优化了这个指标，而且优化得非常成功，从几百毫秒干到了几毫秒，量级上的胜利。

我想要的是「**从按下 ⌘K 到看见第一行结果**」。

在旧方案里，这两个「慢」是重合的——下载和建索引都发生在你等待的那段时间里，压下去一个，另一个跟着下去。而新方案把它们拆开了：查询快了两个数量级，首屏反而多了 0.6 MB。**它优化的指标和我的体感，在这次重构中第一次分了家。**

这不是 Bot 的错。它的测试清单五条，条条合理，每条它都跑通了——**在一台开发机上，用一条快网。** 它没测的那个场景，不是它想不到，是我从来没告诉过它那个场景存在。

这件事我之前用另一个角度写过：[评测集是一份没人签字的文件](https://hugozhu.site/post/2026/384-eval-set-needs-a-signature/)。当时讲的是企业级评测，现在换成一个 388 篇文章的个人博客，逻辑一模一样：

```text
需求提得明确  ≠  把想做的事描述清楚
需求提得明确  =  把「怎样算做完」写下来

我写的：  「搜索变慢了，给个更优方案」
我该写的：「⌘K 到第一行结果 < 1s（4G 网络、冷缓存）；
           加载期间必须有进度反馈；失败必须有可见错误态」
# generated by hugo AI
```

下面那三行如果我一开始就写出来，那个 +98 行的补丁根本不会存在——Bot 完全有能力自己做出来，它只是不知道我在乎。

**在你没定义的维度上，AI 是自由的。** 而它的自由，恰好会落在它能测量的那些指标上。

## 六、「好的工作环境」是四样具体的东西

这次协作里，Bot 干掉了开发、测试、文档、CI 集成——粗算下来八成以上的工作量。我干的是：写一句需求，点一次 Merge，做一次验收。

但这个结果不是「模型变强了」四个字能解释的。同样一个 Bot，如果我的仓库是另一副样子，它一步都走不动。回头看，让它跑起来的是四样很具体的东西：

**一、一份自带上下文的仓库。** Public，内容、模板、构建脚本、CI 配置在同一棵树里。它不需要问我「你的博客是怎么构建的」——`hugo.toml` 和 `.github/workflows/hugo.yaml` 就在那儿。**上下文不是塞进 prompt 的，是长在仓库里的。**

**二、一条有边界的交付通道。** GitHub 账号 + PR。它有独立身份（提交记录上是 `dingtalk-fde`，不是我），交付物有明确边界，而我可以拒绝。这一点在 [Grok Bot 能当队友，还当不了员工](https://hugozhu.site/post/2026/387-grok-bot-teammate-not-employee/) 里我写过——PR 是目前工程界最成熟的「Agent 交付物验收界面」，因为它天生带着 diff、评论和一票否决权。

**三、一条能自己跑到线上的流水线。** merge → Actions → Pages → 钉钉通知。这条链决定了「验收」是一次点击还是一场协调会。

**四、一个写文档的位置。** SEARCH.md 不是给我看的——我大概率不会再读第二遍。它是给下一个来改这块代码的 Agent 看的。这次协作真正沉淀下来的资产，不是那 676 行代码，是那 52 行 markdown。

这四样东西没有一样跟模型能力有关。它们全是 **组织基础设施**，而且全都是在 Agent 到来之前就该有的好工程实践——只不过在人来干活的时候，这些东西缺了可以靠口头沟通补上；换成 Agent 来干，缺了就是硬性阻塞。

## 最后

这次协作里，我一共产出了三样东西：一句需求、一次 merge、一个 +98 行的补丁。

前两样，未来大概率还会继续缩水——需求可以由更好的模板生成，merge 可以设成条件自动化。**唯一不会缩水的是第三样：验收。**

因为验收不是「检查它有没有干完」，验收是「告诉它我到底要什么」的最后一次机会。我那 98 行补丁，本质上是我把一句没说清的需求，用代码的形式补写了一遍。这个补写迟早要发生——要么发生在需求里（便宜），要么发生在验收后（贵一点），要么发生在用户的抱怨里（最贵）。

所以「人只需要把需求提明确，简单验收」这句话里，最重的两个字是 **明确**。它的操作性定义只有一条：**你能不能写出一个让 AI 自己判定「我做完了没有」的标准。** 写不出来的部分，就是你还得亲自去看的部分。

至于那个搜索框——现在按 ⌘K，第一次会看到进度条走完，之后每次都是零网络、几毫秒出结果。我找那篇四年前的 Tailscale 笔记，用了不到一秒。

换成你的团队：你上一次给 AI 派活的时候，验收标准是写在需求里，还是等东西交回来才想起来的？欢迎留言。
