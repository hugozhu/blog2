最近一次架构讨论里，有人把问题抛得很直接：

过去我们建数据中台，是为了让人来运营业务。今天如果要让 AI 来运营业务，是不是需要一个新的中台，姑且叫 AI 中台？系统是不是都要为这个 AI 做好准备？这个 AI 是不是该有最高权限？产品的实现代码和执行日志要不要对它开放？数据是复制一份给它，直接对它开放，还是让它自己决定怎么存取？

五个问题，每一个单拎出来都能吵一下午。但它们其实是同一个问题的不同侧面：**当系统的主要使用者从人变成 AI，中台的重心应该放在哪里？**

<!--more-->

我的回答是：AI 中台需要，但它不是「数据中台 + 大模型」，更不是一个拥有最高权限的超级 AI。它的核心资产不是数据，而是 **可以被安全行动的上下文**。而「AI 要不要最高权限」这个问题本身问错了，真正要设计的是另一个变量：**系统的可逆性。**

下面用一个问题贯穿全文。我在 [Palantir 从本体长到 Agent，我们从 Agent 长回本体](https://hugozhu.site/post/2026/358-palantir-ontology-to-agent-we-grow-back/) 里拿它测过 AI 助手：

> 哪些客户的续约风险正在上升，今天由谁介入？

当时 AI 的回答是「答不了」：它需要同时拉齐 CRM、合同、产品日志、工单、财务五个系统。今天换个问法：如果真要让 AI 不只回答这个问题，而是 **每天自己发现风险、自己安排介入、自己跟进结果**，系统要准备什么？（下文围绕这个问题展开的数字和细节都是示意，用来说明设计取舍，不是某个真实项目的数据。）

## 一、消费者变了，中台的资产就变了

数据中台和 AI 数据底座的区别，我在 [企业知识 AI Ready 的落地路径](https://hugozhu.site/post/2026/249-ai-workflow-events-before-intelligence/) 里写过：数据中台解决的是「数据可见性」，没有解决「数据可行动性」。这里不再展开，只往前走一步：消费者从人变成 AI 之后，中台要多出哪些资产？

| | 数据中台（人来运营） | AI 中台（AI 来运营） |
|---|---|---|
| 主要使用者 | 分析师、运营 | Agent，人在环上监督 |
| 核心产出 | 报表、指标、标签 | 判断和行动 |
| 数据形态 | 聚合宽表，T+1 | 实时事件 + 明细 + 上下文 |
| 链路 | 看数 → 人决策 → 人执行 | 感知 → 决策 → 执行 → 反馈 |
| 核心资产 | 数据 | 上下文 + 行动能力 + 反馈 |

放到续约风险这个例子里，数据中台能给出的是一张「客户健康分」看板。运营同学看到某个客户的健康分从 82 掉到 61，自己去翻工单、问销售、查回款，然后决定要不要找人介入。

AI 来做同样的事，光有健康分不够。它还需要三样数据中台从来不管的东西：

- **为什么**：健康分是怎么算出来的？用量下降是因为客户流失，还是因为上周我们改了埋点？这些答案在指标定义、代码逻辑和变更记录里，不在数仓里。
- **怎么做**：发现风险后，它能做什么？给客户成功经理派一个待办、预约一次回访、申请续约折扣。这些动作得是可以调用的接口，而不是只能在某个后台页面上点。
- **做得对不对**：介入之后客户续约了吗？这次判断是准的还是误报？结果不回流，AI 下个月还会犯同样的错。

所以数据中台的资产不会作废。指标口径、OneData、标签体系都是 AI 中台的底座，只是它们从「终点」变成了「输入」。

## 二、为 AI Ready，关键不是开口子，而是可逆

「系统要为 AI Ready」常被理解成「给 AI 开一个 API」。这远远不够。我会用五条标准去检查一个系统：

1. **能力可描述**：每个业务动作都是带语义说明的工具（MCP 或 OpenAPI + 自然语言描述），AI 知道这个动作是干什么的、什么时候该用、有什么副作用。
2. **行动可预演**：支持 dry-run，AI 能先看到「如果我这样做会发生什么」。
3. **行动可撤销**：操作是幂等的，有补偿或回滚接口；不可逆的操作要显式标记出来。
4. **状态可观测**：日志、trace、业务事件都是结构化的，AI 能看到系统实际发生了什么。
5. **规则显性化**：藏在代码分支和老员工脑子里的业务规则，变成可读的知识。

五条里最容易被忽视、也最关键的是第 3 条。原因很简单：

**你敢给 AI 多大的自主权，不取决于你多信任 AI，而取决于它做错了你能不能撤回来。**

续约风险这个场景里的几个动作，可逆性完全不同：

| 动作 | 可逆性 | 做错的代价 |
|---|---|---|
| 生成风险报告 | 完全可逆 | 浪费一点阅读时间 |
| 给客户成功经理派待办 | 可撤销 | 打扰一个同事 |
| 在内部日历上预约回访 | 可撤销 | 打扰一个同事 |
| 申请 5% 续约折扣（走审批） | 审批前可撤销 | 审批人多看一眼 |
| 直接给客户发邮件 | **不可逆** | 客户看到了就收不回来 |
| 修改合同价格 | **不可逆**（对外承诺） | 真金白银 |

同一个 AI、同一个任务，前四个动作可以放手让它自己做，后两个必须有人拍板。决定这条线的不是 AI 的能力，而是动作本身能不能撤回。

这也意味着，「为 AI Ready」的大部分工作量其实落在业务系统自己身上：补幂等、补补偿接口、补 dry-run、补「这个动作是否可逆」的元数据。这些工作不性感，但它们决定了 AI 中台的天花板。

## 三、AI 该不该有最高权限

不该。但理由不是「AI 不可信」，而是 **任何自动化系统都不该有最高权限**，包括人写的脚本。

关于这个问题的结构性答案，我在 [智能提案，权威拍板](https://hugozhu.site/post/2026/417-intelligence-proposes-authority-decides/) 和 [权限跟着人走，还是跟着工号走](https://hugozhu.site/post/2026/420-permissions-person-or-position/) 里分别写过：智能可以共享，但权限必须有一个明确的主人，AI 只有被委托的权限，上限不超过委托人。这里只补一条落到中台设计上的原则：**读宽写窄。**

**读宽**：AI 的价值来自全局视野。续约风险之所以要 AI 来判断，就是因为没有哪个人会每天同时看五个系统。所以读权限应该相对宽，但要脱敏，并且每一次读取都留审计记录。

**写窄**：写权限按上一节的可逆性分级，而不是按「AI 有多聪明」分级：

```text
L0  只读、分析、出报告              → 默认开放
L1  生成建议，人确认后执行           → 大多数业务动作的起点
L2  可逆动作自主执行（有预算上限）     → 派待办、约回访、重试任务
L3  不可逆 / 高金额 / 对外动作       → 必须人审批，或多 Agent 交叉校验
# generated by hugo AI
```

此外还有三条硬约束：

- **职责分离。** 发现风险的 Agent、执行介入的 Agent、审计结果的 Agent 分开，就像财务里记账和出纳分开。一个 Agent 既发现问题又执行又自我评估，出了错没人能发现。
- **策略不由 AI 制定。** AI 可以建议调整权限策略，但策略的修改必须由人完成。否则就是自己给自己授权。
- **必须有熔断。** 按 Agent、按动作类型设预算上限（每天最多发多少个折扣申请、最多派多少个待办），超了就停，并且要有一键 kill switch。

「给 AI 最高权限」本质上是把整个公司的风险押在一个 prompt 上。哪怕模型本身没问题，一次提示注入、一条脏数据、一个理解错的指令，都会被最高权限放大成事故。

## 四、代码和执行日志要不要开放

这是五个问题里我觉得收益最大、但最常被拒绝的一个。

**代码：开放读权限。** 原因是代码是业务规则最准确的说明书。文档会过时，代码不会，因为线上跑的就是它。

回到续约风险：AI 发现某个客户的「活跃用户数」两周内掉了 40%。是客户真的不用了，还是统计口径变了？如果 AI 能读到指标计算的代码和最近的提交记录，它会发现两周前有一次提交把「活跃」的定义从「登录过」改成了「完成过一次核心操作」。这时候它的结论就不是「高风险，立即介入」，而是「口径变更导致的假阳性，建议排除」。

不给 AI 看代码，它只能对着数字猜。猜错一次，客户成功经理就白跑一趟；猜错几次，就没人再信它的告警了。

代码泄露的担心是真实的，但应该用 **部署边界** 来控制（私有化部署或企业版模型，代码不出域），而不是靠不给 AI 看。

**执行日志：开放，但先过脱敏管道。** 日志是系统「实际发生了什么」，数据库是系统「应该是什么样」。客户说「你们的导出功能坏了三次」，工单里只有一条记录，日志里才有三次失败的 trace。

但日志里常常混着手机号、身份证号、token 和密钥。所以脱敏必须发生在日志进入 AI 可见区 **之前**，由管道统一完成，而不能指望 AI 读到之后自觉忽略。

**反过来，AI 自己的行为日志也必须对人开放。** 它读了哪些数据、为什么判断这个客户有风险、调用了哪些接口、结果如何，全部可查。人让 AI 看到系统的全部，AI 也要让人看到它的全部。这是对等的透明。

## 五、数据：复制、直连，还是让 AI 自己决定

三个选项单独看都不对。答案是按用途分层：

| 用途 | 方式 | 理由 |
|---|---|---|
| 分析和读取 | **不复制**，在现有数仓/湖仓上加语义层和访问策略（行列级权限、脱敏视图） | 复制一份会带来口径漂移、数据新鲜度和双重治理的问题，等于再造一个数据孤岛 |
| 实时感知 | **订阅事件流**（CDC、业务事件） | 不能让 AI 去轮询生产库，会拖垮 OLTP |
| 写入和行动 | **只能走业务 API**，禁止直写数据库 | 业务不变量（库存不能为负、状态机怎么流转）写在应用层，绕过去就会写出脏数据 |
| AI 的工作记忆 | **AI 自己决定**，但限定在自己的沙箱空间，有 TTL 和血缘记录 | 中间结果、缓存、派生特征让 AI 自己管，效率最高 |

「让 AI 自己决定存取」这个选项，我的回答是一句话：

**AI 决定怎么取，人决定能取什么。**

AI 提出一个访问意图，比如「我要看华东区过去 30 天续约到期客户的工单明细」，由策略引擎判断是否放行、以什么粒度放行。AI 可以自由组合查询方式，但不能越过策略边界，也不能修改策略。

用代码表达，大致是这个结构：

```python
from dataclasses import dataclass, field
from enum import Enum
from typing import Protocol


class Decision(Enum):
    ALLOW = "allow"
    ALLOW_MASKED = "allow_masked"   # 放行，但敏感列脱敏
    NEED_APPROVAL = "need_approval"
    DENY = "deny"


@dataclass(frozen=True)
class AccessIntent:
    """AI 提出的访问意图：要什么、为什么要、代表谁。"""
    agent_id: str
    delegator: str            # 委托人，权限上限不超过此人
    dataset: str              # 例如 "support.tickets"
    columns: tuple[str, ...]
    row_filter: str           # 例如 "region = 'east' AND renew_in_days <= 30"
    purpose: str              # 自然语言目的，进入审计日志


@dataclass
class PolicyResult:
    decision: Decision
    masked_columns: list[str] = field(default_factory=list)
    reason: str = ""


class Policy(Protocol):
    """策略只由人维护；AI 只能读取策略，不能修改。"""

    def evaluate(self, intent: AccessIntent) -> PolicyResult: ...


class DelegatedColumnPolicy:
    """按委托人的权限裁剪：委托人看不到的列，AI 也看不到。"""

    def __init__(self, grants: dict[str, set[str]], pii: set[str]) -> None:
        self.grants = grants  # delegator -> 可访问的 "dataset.column"
        self.pii = pii        # 需要脱敏的 "dataset.column"

    def evaluate(self, intent: AccessIntent) -> PolicyResult:
        allowed = self.grants.get(intent.delegator, set())
        wanted = {f"{intent.dataset}.{c}" for c in intent.columns}
        if not wanted <= allowed:
            return PolicyResult(Decision.DENY, reason=f"超出委托人权限: {sorted(wanted - allowed)}")
        masked = sorted(wanted & self.pii)
        if masked:
            return PolicyResult(Decision.ALLOW_MASKED, masked, "包含敏感列，脱敏后放行")
        return PolicyResult(Decision.ALLOW, reason="在委托范围内")


if __name__ == "__main__":
    policy = DelegatedColumnPolicy(
        grants={"csm_lead_east": {"support.tickets.customer_id", "support.tickets.summary",
                                  "support.tickets.contact_phone"}},
        pii={"support.tickets.contact_phone"},
    )
    intent = AccessIntent(
        agent_id="renewal-risk-agent",
        delegator="csm_lead_east",
        dataset="support.tickets",
        columns=("customer_id", "summary", "contact_phone"),
        row_filter="region = 'east' AND renew_in_days <= 30",
        purpose="评估华东区 30 天内到期客户的续约风险",
    )
    print(policy.evaluate(intent))
# generated by hugo AI
```

这段代码里有两个设计值得说明：

- `delegator` 是必填项。没有委托人的访问意图直接不成立，这保证了每一次读取都能追溯到「谁授权的」。
- `purpose` 是自然语言。它不参与判断，但会写进审计日志，事后复盘时能看到 AI 当时「以为自己在干什么」。这比只记 SQL 有用得多。

## 六、一个参考架构

把上面几节拼起来：

```text
┌──────────────────────────────────────────────────────────────┐
│  Agent 层：风险发现 Agent · 介入执行 Agent · 结果审计 Agent         │
├──────────────────────────────────────────────────────────────┤
│  治理层（横切）：委托身份 · 策略引擎 · 审批流 · 预算熔断 · 审计 · Kill Switch │
├────────────────────┬────────────────────┬────────────────────┤
│  上下文层            │  行动层              │  反馈层              │
│  业务本体 / 指标口径   │  工具注册（MCP）      │  行动结果回流         │
│  代码与变更记录       │  dry-run            │  判断准确率           │
│  历史决策与理由       │  幂等 / 补偿 / 可逆标记 │  决策记忆             │
├────────────────────┴────────────────────┴────────────────────┤
│  感知层：业务事件流 · 结构化日志 / trace（已脱敏）· 湖仓（零拷贝 + 语义层） │
├──────────────────────────────────────────────────────────────┤
│  业务系统：CRM · 合同 · 产品 · 工单 · 财务 · 代码仓库                  │
└──────────────────────────────────────────────────────────────┘
# generated by hugo AI
```

和数据中台的分层相比，变化在三处：多了 **行动层**（让 AI 能做事）、多了 **反馈层**（让 AI 知道做得对不对），以及 **治理层从一个模块变成了横切所有层的平面**。

续约风险在这张图里走一遍：感知层收到「某客户活跃用户数下降」事件；风险发现 Agent 在上下文层查到这是口径变更导致的，排除；另一个客户是真实下降，同时工单层有三次导出失败，判为高风险；介入执行 Agent 在 L2 自主给客户成功经理派待办、约回访，在 L3 提交续约折扣申请等审批；一个月后反馈层记录客户是否续约；结果审计 Agent 汇总这一个月的判断准确率。

## 七、最强反方

**反方一：给 AI 读全量代码和日志，是企业能做的最危险的事。宁可复制一份脱敏后的数据集给它，物理隔离最安全。**

这个担心是成立的，尤其当模型跑在企业域外时。我的回应是：复制解决的是「边界」问题，但边界不只有复制这一种做法。

如果模型可以部署在企业域内，那么用策略层和脱敏管道控制边界，比复制更安全。因为复制出来的那份数据，本身就成了一个新的、往往治理更弱的数据资产。如果模型必须跑在域外、且没有可信的数据处理承诺，那复制一份最小化的脱敏数据集确实是合理选择。代价是你要接受口径漂移和数据不新鲜，并且要清楚 AI 的判断质量会因此打折。

所以这不是原则之争，而是部署条件之争。先回答「模型在哪跑」，再决定数据怎么给。

**反方二：这套分级太保守，AI 永远停在 L1，人还是要一个个点确认，那和没有 AI 有什么区别？**

区别在于，分级不是静态的。新员工入职也不会第一天就拿到财务审批权，权限是靠记录挣来的。反馈层的意义就在这里：某类动作在 L1 被人确认了足够多次、准确率稳定，就可以申请升到 L2。升级的依据是数据，决定升级的是人。

我对这件事的把握是：思路是对的，但「多少次、多高准确率才能升级」这个门槛，目前还没有通用答案，要按业务风险一个个定。

## 八、别重蹈中台的覆辙

上一轮中台的教训大家都还记得：先建一个大而全的平台，再等业务来用，结果又重又慢，和业务脱节。

AI 中台更不该这么做。更好的路径是选一个业务闭环，比如续约风险，端到端打通感知、上下文、行动、反馈、治理五层，从 L1 跑到 L2。然后再把过程中长出来的通用部分（工具注册、策略引擎、审计）抽成平台。

这和 [Palantir 从本体长到 Agent，我们从 Agent 长回本体](https://hugozhu.site/post/2026/358-palantir-ontology-to-agent-we-grow-back/) 里的判断是一致的：**平台是从闭环里长出来的，不是先规划出来的。**

## 结尾：中台之争换了一个问题

数据中台时代，最难的问题是「这个数字的口径谁说了算」。为了回答它，企业建了指标体系、数据治理委员会、OneData 方法论。

AI 中台时代，最难的问题会变成「这个动作的权限谁说了算」。它需要的不是另一个更大的数据平台，而是一套新的基础设施：委托身份、可逆性标记、策略引擎、反馈回流。
